# Универсальная AI-платформа новостных порталов — индекс документации

**Статус:** Draft 0.1  
**Дата:** 2026-07-17  
**Назначение:** единая точка входа в техническую и архитектурную документацию проекта.

## 1. Назначение комплекта

Комплект определяет требования к двум независимо устанавливаемым, но совместимым продуктовым шаблонам:

1. **Шаблон новостного интегратора** — поиск, сбор, нормализация, AI-обработка, перевод, дедупликация, формирование новостных пакетов и доставка на сайты.
2. **Шаблон новостного сайта** — получение новостных пакетов, редакционная работа, публикация, SEO/AI-видимость, распространение, аналитика, платежи и реклама.

Каждый установленный интегратор и каждый установленный сайт является самостоятельной сущностью со своей базой данных, административной панелью, конфигурацией, ключами и жизненным циклом. Связи между экземплярами настраиваются по месту. Один интегратор может отправлять материалы нескольким сайтам; один сайт технически может получать материалы от нескольких интеграторов.

Это не MVP. Документация описывает полную согласованную версию продукта. Функции, явно отнесённые к будущему подключению, должны иметь предусмотренные точки расширения, но не считаются реализованными без отдельного требования.

## 3. ADR

Архитектурно значимые решения оформляются в `docs/adr/` и не изменяются молча. Замена решения создаёт новый ADR, который объявляет предыдущий документ superseded.

Планируемый минимум:

- независимые установки и отсутствие общей основной БД;
- модульный monorepo двух продуктовых шаблонов;
- доставка новостных пакетов через API;
- модель `Source Material → Event → Canonical News Package → Site Article`;
- абстракция AI-провайдеров;
- фоновые задачи и очередь доставки;
- S3-совместимое хранение медиа;
- Next.js для публичного сайта и панелей;
- transactional outbox сайта для дашборда;
- раздельные модули платежей и рекламы.

## 4. Приоритет при противоречиях

1. Последнее явно утверждённое бизнес-решение.
2. ADR со статусом `Accepted`.
3. Продуктовые требования.
4. Архитектурная и предметная спецификация.
5. API-контракты и модели данных.
6. Реализация.

Если реализация расходится с документацией, Claude Code не должен самостоятельно объявлять код правильным. Необходимо зафиксировать расхождение и определить, меняется код или спецификация.

## 5. Статусы решений

- **Approved Requirement** — утверждённое бизнес-требование.
- **Recommended Technical Decision** — рекомендуемая реализация, которую можно принять ADR.
- **Open Decision** — решение не принято; должны быть варианты, рекомендация и последствия.
- **Extension Point** — предусмотренная, но не обязательно реализуемая сейчас интеграция.
- **Out of Scope** — сознательно исключённая функция текущей полной версии.

## 6. Обязательная структура каждого предметного документа

Каждый документ, где это применимо, содержит:

- цель и область ответственности;
- утверждённые требования;
- рекомендуемые технические решения;
- функциональные и нефункциональные требования;
- компоненты и основные сценарии;
- модели данных;
- API и события;
- ошибки и пограничные случаи;
- требования безопасности;
- тесты и критерии приёмки;
- зависимости;
- Open Decisions.
